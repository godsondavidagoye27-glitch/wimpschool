# WimpSchool Website Analysis

## Overview

WimpSchool is a static, role-based school management website designed for Nigerian private schools. It uses static HTML pages combined with shared JavaScript modules and a Supabase backend to support:
- School administrators
- Teachers
- Parents
- Super admins

The app is built as a multi-page static website, with each functional area served by its own HTML page and protected with client-side role validation.

## Technology stack

- Static HTML pages in the root folder
- Shared frontend JavaScript modules in `js/`
- Shared CSS in `css/styles.css`
- Supabase backend for authentication, database, and edge functions
- Service worker for offline support in `service-worker.js`
- PWA metadata via `manifest.webmanifest`
- Environment-driven browser config generated by `scripts/generate-config.js`

## Configuration and deployment

### `.env` and `env.example`
- `.env` stores Supabase and Flutterwave configuration values.
- `env.example` documents required keys:
  - `SUPABASE_URL`
  - `SUPABASE_ANON_KEY`
  - `FLUTTERWAVE_PUBLIC_KEY`
  - `SUPER_ADMIN_SECRET`
  - `SENDGRID_API_KEY`
  - `NOTIFICATION_FROM_EMAIL`
  - `TWILIO_ACCOUNT_SID`
  - `TWILIO_AUTH_TOKEN`
  - `TWILIO_FROM`

### `scripts/generate-config.js`
- Reads `.env` or falls back to `.env.example`
- Generates `js/config.js` for browser consumption
- Writes client-side config with keys required for Supabase and payments

### `js/config.js`
- Exposes `window.wimpSchoolConfig`
- Contains browser-safe values only
- Validates Supabase config globally and adds a payment warning on payment pages

### `package.json`
- `npm start` runs `live-server` on port 8000
- `generate-config` writes `js/config.js`
- `postinstall` calls `generate-config`

## Authentication and authorization

### Auth flow
- Uses Supabase Auth via CDN script `@supabase/supabase-js@2`
- `js/auth.js` initializes the Supabase client and exposes helper functions:
  - `getSupabase()`
  - `fetchUserRole(userId)`
  - `signIn(email, password)`
  - `signUpSchoolAdmin(payload)`
  - `sendPasswordReset(email)`
  - `verifyInviteToken(token)`
  - `acceptInvite(token, password)`

### Role management
- The app depends on `user_roles` table for authoritative roles:
  - `school_admin`
  - `teacher`
  - `parent`
  - `super_admin`
- `fetchUserRole()` queries `user_roles` for the current user.
- `js/app.js` enforces role-based page access using `enforcePageRole()`.

### Session persistence
- Sessions are stored in `sessionStorage` or `localStorage` under `wimpschoolUser`
- Session expiry is set to 30 minutes
- `reconcileSessionFromSupabase()` syncs Supabase auth session into local storage

## Data model summary

Main tables in `supabase/schema.sql`:

- `schools`
  - core school settings, branding, plan, billing
- `user_roles`
  - maps auth users to school roles
- `teachers`
  - teacher profiles, invites, classes, subjects
- `students`
  - student profiles, classroom assignments, parent email, student codes
- `parents`
  - parent profiles, invites, linked student
- `parent_student_links`
  - many-to-many parent / student links
- `attendance`
  - attendance records by teacher, student, and status
- `results`
  - academic scores and term entries by teacher
- `payments`
  - fee payment history with transaction references and statuses
- `announcements`
  - school-wide messages
- `notifications`
  - notification records for school users

## Page details and major page flows

### `index.html`
- Landing marketing page
- Navigation links to `register.html`, `login.html`, and `admin.html`
- No role enforcement or backend scripts

### `login.html`
- Unified login form with role selector
- Requires `js/auth.js` and `js/app.js`
- On submit:
  - authenticates via Supabase
  - fetches user role from `user_roles`
  - saves session and redirects to the matching dashboard

### `register.html`
- School onboarding for the first admin
- Captures school details, admin account details, and subscription plan
- On submit:
  - creates Supabase auth user
  - inserts `schools` record
  - creates `user_roles` entry for the new admin
  - redirects to login page

### `forgot-password.html`
- Sends reset link via Supabase auth
- Uses `resetPasswordForEmail()` with redirect back to `login.html`

### `invite.html`
- Accepts an invite token from `?token=` query string
- Supports parent and teacher invitations
- Verifies token against `parents` and `teachers` tables
- Registers account and updates invite state
- Creates a `user_roles` entry upon successful activation

### `admin.html`
- Super admin login screen
- Validates `SUPER_ADMIN_SECRET` via Supabase edge function `super-admin-login`
- Only then signs in with Supabase credentials
- Redirects to `super-admin-panel.html`

### `school-admin-dashboard.html`
- School admin landing page
- Loads metric widgets and notification cards from `js/dashboard.js`
- Uses role enforcement via `data-required-role="school_admin"`

### `student-management.html`
- School admin student creation page
- Supports single student creation and bulk CSV import
- Uses `js/backend.js` for student insert and invite creation

### `teacher-management.html`
- School admin teacher invite and management page
- Inserts teacher records and invite tokens
- Sends notifications to the school notification stream

### `admin-settings.html`
- School admin settings page
- Contains forms for profile, fees, plan upgrades, branding, and notifications
- Uses `data-page="admin-settings"`
- Applies branding preview through `applySchoolBrandingPreview()`

### `announcements.html`
- Publish school announcements to all users
- Creates `announcements` records in Supabase

### `fee-management.html`
- Fee-related configuration and tracking
- Allows admins to set class fee structures and review payments

### `timetable.html`
- Timetable management page for school admins
- No explicit scripts beyond `js/app.js` and common modules

### `teacher-dashboard.html`
- Teacher homepage summary
- Purposes:
  - attendance quick links
  - result entry quick links

### `attendance.html`
- Teacher attendance entry page
- Stores attendance records in `attendance` table

### `results.html`
- Teacher result entry and bulk upload page
- Accepts `student_code` from CSV and maps to actual `student_id`
- Inserts `results` records

### `parent-portal.html`
- Parent dashboard showing child profile, balances, and payments
- Loads parent/student relationship data from `parents`, `parent_student_links`, and `students`
- Integrates Flutterwave checkout via `js/payments.js`
- Records payments in the `payments` table

### `super-admin-panel.html`
- Super admin portal
- Protected by `data-required-role="super_admin"`
- Uses `js/app.js` for session enforcement

## Shared frontend architecture

### `js/app.js`
- Core application engine for page lifecycle
- Registers service worker and install prompt
- Handles session save/load/clear
- Enforces role-based access for protected pages
- Loads page-specific scripts depending on `data-page`
- Attaches logout behavior
- Provides utility formatting functions

### `js/auth.js`
- Initializes Supabase client
- Handles auth, registration, password reset, and invite acceptance
- Contains Supabase role lookup and fallback logic

### `js/backend.js`
- Domain helpers for school operations
- Creates students, teachers, parents, attendance, results, payments, announcements, notifications
- Supports CSV import and template download
- Uses Supabase functions when available for notifications and role management

### `js/dashboard.js`
- Dashboard-specific logic and metrics
- Fetches counts, notifications, recent payments, and fee chart data
- Exports dashboard summary in multiple formats

### `js/payments.js`
- Payment flow for parent portal
- Loads the Flutterwave checkout script dynamically
- Initiates payment with `window.FlutterwaveCheckout`
- Records the payment on completion

### `js/invite.js`
- Invite activation page logic
- Verifies tokens and activates parent/teacher accounts

### `js/config-checker.js`
- Validates frontend config on page load
- Shows an inline banner if config is missing or incomplete

## PWA and offline support

### `service-worker.js`
- Caches app shell assets and pages
- Installs and activates with cache versioning
- Intercepts navigation requests and returns `offline.html` when offline
- Caches assets individually to avoid install failures if one file is missing

### `manifest.webmanifest`
- Provides PWA metadata and icons
- Defines standalone display, theme and background colors

## How the app works end to end

1. A visitor arrives at `index.html`.
2. They can register a new school, log in, or access super admin login.
3. `register.html` creates a new school and school admin account.
4. `login.html` authenticates users and determines their role from `user_roles`.
5. The app redirects users to the role-specific portal:
   - `school-admin-dashboard.html`
   - `teacher-dashboard.html`
   - `parent-portal.html`
   - `super-admin-panel.html`
6. Once logged in, page access is protected by `js/app.js` role enforcement.
7. School admins manage students, teachers, fees, announcements, and settings.
8. Teachers take attendance and enter results.
9. Parents view child status and make payments via Flutterwave.
10. Notifications are stored in Supabase and optionally routed through edge functions.

## Critical implementation notes

- Role protection is enforced in `js/app.js` on page load using Supabase session and `user_roles`.
- `js/config.js` is generated at install/build time from `.env`.
- The site relies on client-side logic; server-side access control is handled by Supabase RLS configuration and edge functions behind the scenes.
- `user_roles` is the authoritative role table for portal access.
- `payments.js` requires a valid `FLUTTERWAVE_PUBLIC_KEY` only on pages that actually initiate payments.
- `admin.html` uses a secret validation edge function for super admin access.

## Current gaps and risks

- The site is largely static and uses client-side role enforcement, which means proper Supabase RLS and edge function security are essential.
- Some pages do not include any backend script and are static marketing/policy pages.
- The `config.js` generation process can be fragile if `.env` values are missing; the code now falls back to `.env.example`.
- Super admin access requires an edge function and `.env` secret configuration.
- The service worker caches `js/config.js`, which is required for offline reliability.

## How to run

1. Copy `.env.example` to `.env`
2. Populate `SUPABASE_URL`, `SUPABASE_ANON_KEY`, and `FLUTTERWAVE_PUBLIC_KEY`
3. Run `npm install`
4. Run `npm start`

## Conclusion

WimpSchool is a static-javascript-driven school management website with clearly separated role-based portals. It combines Supabase auth and database operations with a generated browser config model and PWA/offline support. The key user journeys are:
- school registration and admin onboarding
- teacher attendance and result workflows
- parent portal and payment workflow
- super admin oversight

The architecture is straightforward: static pages, shared JS modules, and Supabase for backend power. The analysis above covers every page, the navigation and role flows, the core scripts, and the database model used by the site.
